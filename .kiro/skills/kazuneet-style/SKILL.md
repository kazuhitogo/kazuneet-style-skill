# kazuneet 文体スキル

呉和仁の公開記事 56 本 (Qiita 40 / Zenn 4 / builders.flash 12) を分析して抽出した、構成と文体のルール。
元記事は `kazuhito_go_articles/` にある。細かい例文は `references/examples.md`、媒体別の型は `references/templates.md`。

## 最優先の原則

1. 実際に検証した内容だけを書く。コード、出力、数値、所要時間、失敗を捏造しない。検証結果が手元に無ければ、先にユーザーへ聞く。
2. 一次情報 (公式ドキュメント、What's New、論文) の URL を先に貼り、それを読んだ読者に向けて「自分が試した差分」を書く。
3. 文体は「丁寧語のまま友達に話す」。堅い文書調に寄せない。技術的な主張は慎重、語り口は軽い。

## 文体ルール

### 文末
- 基本は「です・ます」。実測で「ます」約 44%、「です」約 16%、「ました」約 11%、「ましょう」約 4%、「ません」約 4%。
- 「だ・である」は使わない。体言止めは見出し、箇条書き、ツッコミの括弧内だけ。
- 提案は「〜しましょう」「〜しような！」(砕けるときだけ)。
- 結論に自信がないときは言い切らず、「たぶん。」「(しらんけど)」「〜っぽいです」「〜はず」で止める。ぼかしを隠さない。

### 語り口
- 一人称は主語として多用しない。「私」は builders.flash の自己紹介や、括弧内の補足 (`（私がハマった）`) で使う程度。
- 読者への呼びかけは「みなさま」「Builder の皆様」程度。
- 括弧の独り言ツッコミを 1 記事に数回入れる。例: `(結局 ModelId 引数を使うのね)`、`（確認したつもり何だがなぁ）`、`（小並感）`、`（早くもチートのかほり）`。
- 感嘆は「！」。「！！」は 1 記事に 1〜2 回まで。
- 笑いは顔文字や「w」ではなく、言葉の選びで出す。パロディ、漫画やゲームの台詞のもじり、大げさな比喩を使う。
- ネタは本題の技術と対応させる。例: クオータを食い尽くす話に「◯してやるぞ」(漫画台詞のもじり)、親の威厳を取り戻す話に Minecraft。ネタのためだけに脱線しない。
- ネタが危うい場合は冒頭に注意書きを置く。例: `:::note warn` で「紳士淑女にふさわしくない表現が多々現れます」。

### 表記
- 英数字と日本語の間は半角スペースを空ける (`Amazon Bedrock を試す`、`3 分で`)。数字と単位の間も空ける (`8 時間`、`3 分`)。
- 括弧は全角 `（）` と半角 `()` が混在する。コード寄りの語は半角、文中の補足は全角でよい。
- サービス名は正式名称で書き、2 回目以降は短縮してよい (Amazon Bedrock → Bedrock、AgentCore)。
- 日付は `2025/8/12` 形式。情報の鮮度を残すために書く。

## 記事の構成

### 1. タイトル
次のどれかの型にする。
- `〜を試す` / `〜を試してみた` / `〜を試してみたよ`
- `〜が出た (GA した) ので〜してみた`
- `〜してみた話` / `〜と戦って改善した話`
- `〜の使い方`
- 技術名 + 一言のフック。例: `人間の実働 3 分で Runtime を動かす`、`最も短いコード`
- 論文や記事の翻訳は先頭に `【翻訳】` を付ける。
- シリーズは `①②③` か `前編/後編` で番号を振る。
- ネタ寄りのタイトルは、正式な技術名を必ず含める。検索で見つかる状態にする。

### 2. 冒頭 (最初の 3〜10 行)
次のいずれかで始める。
- 一次情報の URL を貼り、「出ました。」のような一言を添える。
- `今北産業すると、` に続けて 3 行の箇条書き (何が / どうなって / 何ができる)。
- 背景の悩みを 2〜3 文で書き、「そんなとき〜できるのか、というお話」と受ける。
- シリーズ物は「前回は〜でした」と前の記事のリンクと要約から入る。
- 初回投稿は自己紹介を一言。

その後、この記事で何をやり、何をやらないかを 1〜2 文で言う。例: 「裏側の動作には触れず、どうやって動かすか、にフォーカスします」。

### 3. 本文
- 見出しは `##` を中心に、短い動詞句や名詞で付ける。頻出: `やってみる`、`試す`、`実行`、`結果`、`コード`、`準備`、`手順`、`概要`。
- 手順は「まずは〜しましょう」で始め、1 手順につきコードブロックを 1 つ置く。
- 公式ドキュメントを読みながら進める場合は、該当ページの URL を各手順の前に貼る。
- コードブロックには言語とファイル名を付ける。例: ` ```python:main.py `、` ```json:出力 `。
- コードの直後に、何をしているかを 2〜3 文で言葉にする。コードを説明なしで並べない。
- 比較や検証は、条件 (リージョン、モデル、回数、入力) を先に書き、結果を後に書く。結果が表で収まるなら表にする。
- つまずいた点、エラーメッセージの原文、失敗した結果もそのまま載せる。例: 「やはり日本語はダメでした」。
- 自分の検証が不十分な箇所は、断定せずに「確信をもっていないのでなんともですが」と書く。

### 4. 締め
次のどれかで締める。
- `まとめ` に要点を 2〜4 文か箇条書きで書く。
- `以上、〜でした。` (例: 以上、雑検証でした。以上、とりあえずやってみたでした。)
- 軽い締め。例: `ちゃんちゃん。`、`では〜`。
- 次にやることの予告か、シリーズの記事一覧へのリンク。
- 情報の鮮度の注記。例: 「2025/8/12 の情報なので、アップデートが走ってもしりません」。
- 全体を通して、読者に行動を促す一文を 1 つ入れる。例: 「ぜひ使ってみてはいかがでしょうか」。

## 媒体別の差

- **Qiita**: 最も砕けた口調。短く、手を動かした記録が中心。`今北産業`、`tl;dr` を使う。
- **Zenn**: Qiita と同じ口調で、少し長く丁寧。`この記事は？`、`前提`、`やってみよう` の見出しを使う。イベント参加記事は、冒頭にイベント名とハッシュタグを書く。
- **builders.flash (公式ウェブマガジン)**: 自己紹介から入る物語調。冒頭で日常の小話やボケを 1〜2 段落置き、その後に本題へ入る。見出しは `〜とは？`、`結局何をしたのか？`、`環境作成` など。共著や対談形式 (呉「」/ 相手「」) もある。免責 (料金がかかる旨) の定型文を入れる。

詳細な型は `references/templates.md` を参照。

## 書くときの手順

1. 題材、検証した環境、実行結果、公式 URL をユーザーから受け取る。足りなければ聞く。
2. 媒体 (Qiita / Zenn / builders.flash) を決める。指定が無ければ Qiita 型を使う。
3. `references/templates.md` の型に沿って見出しを組む。
4. 本文を書く。コードと出力はユーザーが提供したものだけを使う。
5. 末尾のチェックリストで自己点検する。

## チェックリスト

- [ ] 冒頭 10 行以内に、何の記事かと一次情報の URL がある。
- [ ] 文末が「です・ます」で統一されている (ネタの台詞を除く)。
- [ ] 括弧の独り言ツッコミが 2〜6 箇所ある。多すぎない。
- [ ] コードブロックにファイル名か言語名が付いている。
- [ ] コードの直後に説明がある。
- [ ] 検証条件 (日付、リージョン、モデル、バージョン) が書いてある。
- [ ] 失敗や不確実な点を隠していない。
- [ ] 締めの 1 行が `以上、〜でした。` か近い型になっている。
- [ ] ネタがタイトルだけで終わらず、本文の技術と対応している。
- [ ] 検証していない結果や数値を書いていない。
